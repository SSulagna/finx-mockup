Party Lifecycle Management

The Party Lifecycle Management service domain orchestrates a customer party from initial onboarding to active status. It maintains lifecycle state and phase transitions, coordinates Identity Proofing through Jumio and AML / PEP screening through ComplyAdvantage, records customer status flags via Precedents, and references documents held in the Document Directory. It is the authoritative lifecycle orchestrator, not the customer master record.

Scope. This SD orchestrates lifecycle state and assessment coordination. Customer profile master data lives in Party Reference Data Directory; document artefacts live in Document Directory; identity verification execution belongs to Jumio; AML and PEP screening execution belong to ComplyAdvantage.

What Is This Service Domain?

In BIAN v14.0, the Party Lifecycle Management (PLM) Service Domain maintains and orchestrates the onboarding lifecycle of a customer party, tracking their progression through onboarding phases and managing identity, qualification, and status updates associated with a specific Party Instance.

Role: PLM acts as the authoritative lifecycle orchestration layer for a given partylifecyclemanagementId (Party Instance Reference). It initiates, updates, and tracks the end-to-end party lifecycle, from initial customer offer acceptance through identity verification, qualification assessment, and final party creation.

Classification: This is a Party Lifecycle Orchestration Domain, not a data store, not a verification engine, not a screening platform. It strictly orchestrates lifecycle state transitions and assessment coordination.

Behaviour Qualifier Structure

Four Behaviour Qualifiers are implemented in the current scope:

Behavior QualifierCardinalityPurpose
IdentityProofing1..*Orchestrates Jumio IDV workflow asynchronously; stores Account API and Fetch Result responses for audit
Qualification1..*Triggers ComplyAdvantage AML/PEP screening; persists full CA workflow response including risk score and step details
Precedents1..*Records each customer status flag (ResidentialStatus, SeniorCitizen, IDVStatus, AMLStatus, PEPStatus) as a separate independently addressable BQ instance
Documentation1..*Records Document Directory reference IDs against the lifecycle instance; document artifacts remain in Document Directory SD

All four BQs have 1..* cardinality, multiple instances can exist under the same lifecycle Control Record. Each instance is independently addressable via its BIAN-standard path parameter (identityproofingid, qualificationid, precedentsid, documentationid).

Onboarding Lifecycle Flow

PLM is invoked at each lifecycle milestone throughout the customer onboarding journey:

Lifecycle EventEndpoint InvokedKey Action
Application InitiationPOST .../InitiateCreate CR; set lifecycle phase to IdentityVerification; status In Progress
Application ID LinkagePUT .../UpdateStamp Customer Offer Application ID against PLM CR via WorkProductIdentifoication
Document Reference RecordingPUT .../Documentation/{id}/UpdateRecord Document Directory reference IDs; one call per document
Identity Proofing InitiationPOST .../IdentityProofing/InitiateTrigger Jumio IDV async workflow; return BQ ID; store Account API response
Identity Proofing Result PollingGET .../IdentityProofing/{id}/RetrievePoll PLM DB for Jumio Fetch Result; no Jumio API call triggered
AML/PEP Screening InitiationPOST .../Qualification/InitiateTrigger ComplyAdvantage with full customer profile JSON; persist full CA response
Qualification Update (if needed)PUT .../Qualification/{id}/UpdateAmend assessment record on manual review decision or result correction
Post-Assessment Status UpdatePUT .../UpdateAdvance lifecycle phase; set party name (now confirmed from PRDD)
Customer Status Flag RecordingPOST .../Precedents/Initiate (x5)Register each flag as a separate Precedent BQ instance (5 flags total)
Onboarding CompletionPUT .../UpdateSet phase to OnboardingComplete and status to Completed; close lifecycle loop

Application Initiation

When a customer submits an onboarding application, POST /PartyLifecycleManagement/Initiate is called to establish the onboarding session anchor. Initial lifecycle phase is set to IdentityVerification; status is In Progress. The Application ID is generated by Customer Offer SD, not by PLM.

Application ID Linkage

Once Customer Offer SD generates the Application ID, it pushes the ID into PLM via PUT .../Update. WorkProductIdentifoication.IdentifierValue carries this ID forward across all lifecycle events, linking PLM and Customer Offer SD to the same anchor reference.

Document Reference Recording

PLM calls Document Directory SD to create a document entry for each submitted document. The returned Document Directory reference ID is then recorded in the Documentation BQ via PUT .../Documentation/{documentationid}/Update. Document artifacts remain in Document Directory SD, PLM holds only the reference IDs.

Post-Assessment Lifecycle Status Update

Once IDV and AML assessments are both complete, PUT .../Update is called to advance the lifecycle phase and set the party name (now confirmed from PRDD). This update must occur before Precedent flag recording.

Onboarding Completion

Once all downstream SDs (PRDD, Customer Offer, Savings Account, Customer Agreement, CPSD) are successfully created and their procedures closed, PUT .../Update is called a final time to set the lifecycle phase to OnboardingComplete and status reason to Completed.

Identity Proofing BQ, Jumio Integration

Initiate Flow

POST /PartyLifecycleManagement/{id}/IdentityProofing/Initiate triggers the Jumio IDV workflow. The channel passes user consent and Document Directory IDs. The adapter returns the Identity Proofing BQ ID immediately and then asynchronously orchestrates the complete 10-step Jumio sequence.

Mandatory Task JSON attributes: userConsent.userIp, userConsent.userLocation.country, userConsent.userLocation.state, userConsent.consent.obtained (must be exactly 'yes'), userConsent.consent.obtainedAt. Any missing or invalid value causes immediate rejection.

Retrieve Flow

The channel polls GET .../IdentityProofing/{identityproofingid}/Retrieve until a terminal result is returned. The Retrieve endpoint reads entirely from the PLM database, no Jumio API calls are triggered. The channel reads IdentityProofingTaskResult.AssessmentResult to determine the verification outcome for screen display.

No Update endpoint exists for Identity Proofing. The adapter writes the Jumio Fetch Result response back into the same BQ record internally during asynchronous processing.

Payload Enhancements, Identity Proofing BQ

  • SpecialistAgencyServiceRequestResult modeled as array (1..*): InstructionDescription[0] = Jumio Account API JSON; InstructionDescription[1] = Jumio Fetch Result JSON. Both retained for audit.
  • DocumentDirectoryEntryInstanceReference modeled as array (1..*): front and back image document references stored separately.
  • IdentityProofingReference.IdentifierValue (BQ ID) used as customerInternalReference in Jumio Account API, unique traceability between PLM record and Jumio session.
  • Workflow definition key 2, face/selfie not required; only front and back ID document images needed.

Qualification BQ, AML/PEP Screening

Initiate Flow

POST .../Qualification/Initiate triggers the ComplyAdvantage screening workflow. The full customer profile (name, DOB, nationality, address, IDs, contact, profession, source of wealth) is serialized as a JSON string and passed inside QualificationTaskRecord.Task. The complete CA workflow response is persisted: workflow_instance_identifier in InstructionIdentification, overall status in InstructionStatus, step-level JSON in InstructionResult and InstructionDescription.

Update Flow

PUT .../Qualification/{qualificationid}/Update is used post-initiation when a manual compliance review decision is made for a REVIEW_REQUIRED outcome, or when a correction to the screening result is needed.

AML/PEP Decision Logic

InstructionResult and AssessmentResult are derived from two CA step output fields:

  • step_details.initial-risk-scoring.step_output.overall_level
  • step_details.customer-screening.step_output.screening_result

Precedents BQ, Customer Status Flags

POST .../Precedents/Initiate is called once per status flag. Each flag is a separate, independently addressable Precedent BQ instance. Five flags are recorded during onboarding:

PrecedentTypePrecedentValue (example)
ResidentialStatusResident / NonResident / NRI / OCI / PIO / RNOR / ForeignNational
SeniorCitizenYes / No
IDVStatusAPPROVED / WARNING / REJECTED / NOT_EXECUTED
AMLStatusclear / on hold / failed
PEPStatusNO_PROFILES / PROFILES_FOUND (true → PoliticallyExposedPerson, false → NotPEP)

PrecedentType values are not hardcoded. The orchestration layer reads the PrecedentType and maps it to the corresponding value. PEPStatus is boolean: true → PoliticallyExposedPerson; false → NotPEP.
