Position Keeping

The Position Keeping service domain records and exposes individual financial postings against an account: transaction lines, value dates, posting amounts, and counterparty references. It is the authoritative source for transaction-level account history.

What Is This Service Domain?

It acts as the authoritative transaction ledger exposure layer for a given positionkeepingid (Account Instance Reference).

Key Distinction

AttributeDetail
What it managesLedger-level transaction entries, identification, date, description, amount, debit/credit indicator, status
What it does NOT doManage customer profile data, belongs to Party Directory SD
What it does NOT doManage product agreement configuration, belongs to Sales Product Agreement SD
What it does NOT doMaintain customer holdings registry, belongs to Customer Product & Service Directory SD
What it does NOT doPerform payment execution, belongs to Payment Execution domain
Primary roleAuthoritative transaction ledger exposure layer, read-only in current scope
positionkeepingidAccount Instance Reference, unique identifier per account position record

Behaviour Qualifier in Scope

The existing FinancialTransactionCapture BQ is used. No new Behaviour Qualifier was introduced. All enhancements remain within the existing BIAN structure.

BQ AttributeDetail
BQ NameFinancialTransactionCapture
Cardinality1..*, Multiple transaction entries can exist under the same Position Keeping CR. Each entry is independently addressable via financialtransactioncaptureid in the path.
BQ IDfinancialtransactioncaptureid, BIAN-standard BQ instance identifier. In this implementation, both positionkeepingid and financialtransactioncaptureid are passed with the same account number (to preserve BIAN endpoint structure without deviation).
Implemented OperationRetrieve only, GET /PositionKeeping/{positionkeepingid}/FinancialTransactionCapture/{financialtransactioncaptureid}/Retrieve
Not implementedInitiate, Update, Control, Initiate CR, Position Recalculation

When to Use This Service Domain

This SD is invoked when transaction-level history retrieval is required for a specific account. Current scope supports read-only retrieval only.

ScenarioAction
Transaction History View Customer opens Transaction History screen in mobile/internet banking.Call GET /.../FinancialTransactionCapture/{id}/Retrieve with fromDate, toDate, and pageSize query parameters. Fetches transactions within the date range with pagination support for infinite scroll UI.
Statement Generation Customer requests account statement for a defined period.Invoke the same Retrieve endpoint with fromDate = statement start date and toDate = statement end date. Returned transactions are compiled into a statement document.
Operational or Audit Review Operations or audit team reviewing account activity.Retrieve endpoint invoked with date filters and pageSize for controlled, paginated result extraction. Supports reconciliation and audit.

Level of Details to Capture

This is an Operational Ledger Exposure Domain. Each transaction entry must capture:

Data ElementPurpose
Transaction IdentificationUnique identifier for each ledger entry, for internal reference and audit traceability
Transaction DateBooking date of the transaction, when it was posted to the ledger
Transaction DescriptionHuman-readable description, merchant name, reference, or payment description
Transaction AmountExplicit monetary value of the ledger entry with currency, no ambiguity of implicit values
Debit / Credit IndicatorExplicit classification of transaction direction (Debit/Credit), avoids relying on positive/negative amount inference
Transaction StatusStatus of the transaction (e.g. Completed / Rejected), derived from upstream posting system status
Transaction Status Type ValueBIAN enum value for status, Completed / Rejected / Initiated etc.
Event IdentificationClient batch ID from the posting system, provides traceability back to the originating posting batch

Query Parameters

The following query parameters are supported on the Retrieve endpoint to filter and paginate transaction results:

Query ParameterPurpose
fromDateStart date for transaction filtering, only transactions on or after this date are returned
toDateEnd date for transaction filtering, only transactions on or before this date are returned
pageSizeMaximum number of transaction records to return per call, supports paginated UI / infinite scroll
The API response must include next page and previous page tokens to support subsequent paginated calls when the result count exceeds pageSize.

BIAN Specification Enhancements

The following enhancements were introduced while preserving Service Domain boundaries:

EnhancementDetail
TransactionAmount addedExplicit monetary value of the ledger entry using a structured Amount object including currency. Avoids ambiguity of implicit amount fields.
TransactionDebitCreditIndicator addedEnum: Debit / Credit. Provides explicit classification of transaction direction. Avoids relying on positive/negative amount sign inference. Ensures semantic clarity for consuming systems.
FinancialTransactionCapture BQ → 1:*BQ is modeled with cardinality 1..*, multiple transaction entries exist under the same CR, each independently addressable via financialtransactioncaptureid.
Query parameters: fromDate, toDate, pageSizeAdded to the Retrieve endpoint to support date-range filtering and result pagination.
Pagination tokens in responsenext page and previous page tokens must be returned in the response to support subsequent paginated calls.
No own DB schemaThis SD does not require its own schema. It connects directly to the core target adapter to pull transactions from the core posting system.

Boundary Integrity

All enhancements remain within Position Keeping SD scope and do not violate service domain boundaries:

Boundary RuleExplanation
Ledger entries onlyRepresents ledger-level transaction data only, not customer or product data
No posting orchestrationDoes not introduce payment initiation or posting orchestration, belongs to Payment Execution domain
No overlap with AccountingDoes not perform ledger recalculation or accounting, that belongs to accounting domains
Payment Execution boundary intactPosition Keeping exposes results of completed postings, it does not execute them
