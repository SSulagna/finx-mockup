Term Deposit

In BIAN v14.0, the Term Deposit Service Domain maintains and exposes the operational state, balances, restrictions, entitlements, and lifecycle attributes associated with a specific AccountInstanceReference.

What Is This Service Domain?

BIAN defines this SD as responsible for managing and exposing the live operational representation of a term deposit account instance. It follows the same implementation pattern as the Savings Account and Current Account SDs, with additional term-deposit-specific fields.

Classification: This is an Operational Account Instance domain, not a directory or contract domain.

Key Distinction

Term Deposit SD ManagesTerm Deposit SD Does NOT Manage
Runtime account state and statusCustomer profile data, Party Directory SD
Account balances (available, incoming, outgoing, accrued interest)Product agreement configuration, Sales Product Agreement SD
Entitlements (product & account level parameters)Customer holdings registry, CPSD SD
Restrictions (templates & account instances)Other CR/BQ endpoints (future phases)
Lifecycle timestamps (open, effective, creating)
TD-specific fields: amount, duration, maturity date, open date

When to Use This Service Domain

Invoke the Term Deposit SD whenever real-time term deposit account state must be retrieved or reflected in any consuming system or channel.

During Account Dashboard View

Scenario: Customer logs into digital banking.

Action: Application retrieves account state through Term Deposit SD to display balances, currency, status, account details, and account parameters.

During Balance Inquiry

Scenario: User checks current deposit balance.

Action: System retrieves real-time data from GET /v1/balances/live, mapped to accountbalances[] in the BIAN payload.

During Product Rule Display

Scenario: UI needs to display deposit rules such as tenure, penalty rates, and interest rates.

Action: Values sourced from entitlementoptiondefinition[] (product-level) and entitlementoptionsetting[] (account-level).

Freeze and Unfreeze Account

  • The bank operator can freeze or unfreeze an account, restricting all transactions to and from it.
  • This operation triggers when the update API is called and the fields for restriction templates and instances are populated.
  • Only the bank operator can initiate this operation; customers cannot request a freeze or unfreeze.
  • Only transactions are restricted on frozen accounts; customers can still access their accounts and view documents.
  • No notification is sent to customers when their accounts are frozen or unfrozen.

Level of Detail to Capture

Captured data must be:

  • Instance-specific, all data must relate to the specific AccountInstanceReference.
  • Runtime accurate, balances and status sourced live from TM; no cached data.
  • Balance-aligned, balance types correctly mapped to TM posting phases including accrued interest.
  • Lifecycle-aware, OpenDate only populated when StatusReason = OPEN.
  • Externally sourced, all operational data sourced from four TM upstream APIs.

Relationship Model

For each AccountInstanceReference (e.g. TD-ACC-556677), multiple records exist inside arrays:

Account Lifecycle Flow

StepDetail
Step 1, InitiatePOST /TermDeposit/Initiate → POST /v2/accounts with empty parameters and status ACCOUNT_STATUS_PENDING
Step 2, Return account_idTM returns account_id; orchestration layer triggers Update
Step 3, Apply ParametersPOST /v1/parameter-values:batchCreate with TD-specific parameters from EntitlementOptionSetting[]
Step 4, Activate AccountPUT /v2/accounts/{account.id} → status transitions ACCOUNT_STATUS_PENDING → ACCOUNT_STATUS_OPEN

Status Lifecycle

  • ACCOUNT_STATUS_PENDING, account created in CBS; TD parameters not yet applied.
  • ACCOUNT_STATUS_OPEN, account activated; TD parameters applied; fully operational.
