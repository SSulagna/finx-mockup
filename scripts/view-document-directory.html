Document Directory

The Document Directory service domain stores and indexes customer-related documents: identity artefacts, address proofs, agreement copies, and supporting evidence. It is the authoritative store for document artefacts; other service domains hold only references.

What Is This Service Domain?

The Document Directory Service Domain in BIAN v13.0 is responsible for recording and exposing document entries, specifically the storage path URLs of documents collected, generated, or uploaded across any banking process.

It acts as the authoritative document registry and reference layer for a given documentdirectoryid (Document Directory Instance Reference). The actual binary files are stored in any compatible external storage system, only the URLs and metadata persisted in this SD.

Key Distinction

AttributeDetail
What it managesDocument metadata and storage location references (URLs)
What it does NOT doStore actual document files, binaries live in the external storage system
Primary roleAuthoritative document registry and reference layer across banking processes
Identifierdocumentdirectoryid, Document Directory Instance Reference, unique per registered document

When to Use This Service Domain

This Service Domain can be invoked across any banking process or journey wherever document metadata and storage location references need to be registered or retrieved. It is not limited to any specific journey.

As part of the current implementation scope, it is being used during the customer onboarding journey. The same SD will be reused as-is whenever other journeys require document registration or retrieval, no changes to the SD will be needed.

Invocation Scenarios

ScenarioBIAN OperationDescription
Register a DocumentPOST /DocumentDirectory/RegisterOnce a document is uploaded to a compatible storage system and a storage URL is obtained, invoke Register to persist document metadata and URL for future retrieval and audit.
Retrieve a DocumentGET /DocumentDirectory/{documentdirectoryid}/RetrieveRetrieve the stored file path from the Document Directory, then use the returned URL to access the document from the storage system. Enables viewing, audit, or downstream processing.

Prerequisite

Documents must be uploaded to any compatible storage system BEFORE invoking the Document Directory endpoints. The APIs for document upload to the storage system are outside the scope of this Service Domain and must be handled separately.

SD Scope, Level of Details to Capture

This is an Operational Document Registry Service Domain, not a content store. Data captured must be metadata-accurate, location-referenced, and status-aware.

CategoryDetails Captured
Document IdentityDocument Type, Document Identifier Value (e.g. Passport Number)
Document DatesCreation Date, Capture DateTime, Signing Date, Issue Date, Validity From / Validity To
Issuing AuthorityAuthority Name, Authority Type, Party Involvement Type
Storage LocationStorage URL / File Path (DocumentLocation), mandatory field
Document ContentDescription, Subject, Purpose, Format (file type)
Document StatusActive / Expired / Rejected, drives integration flows

Behaviour Qualifiers (BQs)

No Behaviour Qualifier endpoints were introduced in this implementation. All operations are at the Control Record (CR) level only.

Cross-SD Traceability

The documentdirectoryid returned by POST /DocumentDirectory/Register must be stored in the relevant Service Domain via DocumentDirectoryEntryInstanceReference for cross-SD traceability.

Example: Party Reference Data Directory SD stores this parameter in its CIF DB so it can call GET /DocumentDirectory/{documentdirectoryid}/Retrieve to retrieve any party-related documents when needed.

BIAN Version Note

The BIAN V14 published API payload for Document Directory is currently insufficient and is a work in progress. The current implementation is based on BIAN V13 temporarily and will be upgraded to V14 once BIAN publishes the complete specification.
