Product Directory

The Product Directory service domain defines the catalogue of bank products available for sale: current accounts, savings accounts, term deposits, and their variants. It carries product configuration, eligibility, and lifecycle status.

What Is This Service Domain?

In BIAN v14.0, the Product Directory Service Domain maintains and exposes the catalog of financial products offered by the institution. It is the authoritative source of product definitions and configuration templates, referenced by other Service Domains when products are instantiated or used.

The Product Directory manages: Product Identity, Product Classification, Operational / Sales & Marketing / Servicing & Production Requirements, and Product Features & Specifications.

Classification: This is a Product Definition Domain, not a runtime domain, not a customer-specific domain. Data is product-level, configuration-driven, variant-specific, and institution-defined.

Key Distinction

Product Directory SD ManagesProduct Directory SD Does NOT Manage
Product definitions and configuration templatesCustomer agreements, Sales Product Agreement SD
Product identity, classification, and featuresCustomer product holdings, CPSD SD
Variant-level feature configurationsOperational account state, Savings/Current Account SDs
Sales and marketing product attributesCustomer-specific settings or runtime data
Product eligibility and suitability definitionsLive account balances or transaction states

Implementation Scope

Standard BIAN Product Directory structure is retained. Minor enhancements align the model with the Enterprise Business Object Model (BOM), CR Diagram, and Thought Machine product structures.

Product Hierarchy Model

Products in Thought Machine are structured in a three-tier hierarchy exposed through the Product Directory:

LevelDescription
Product FamilyTop-level product group (e.g. current_account). Retrieved via GET /v1/products. One CR per product family.
Template (LEVEL_TEMPLATE)Base product definition within a family. Contains the foundational parameter set. Identified by tags[0] = LEVEL_TEMPLATE.
Variant (LEVEL_VARIANT)Specific product offering derived from a template. Identified by tags[0] = LEVEL_VARIANT and PARENT_VERSION tag linking back to template.

ProductReference[], CR Array

A ProductReference field is used inside the CR payload. ProductReference is an array of Product objects where each element represents one product version (template or variant) of the same core product family.

ProductIdentification is also structured as an array within each ProductReference element, allowing multiple identification types per product version:

ProductIdentificationTypeExample ValuePurpose
Suppliersitemnumbercurrent_accountProduct family / smart contract ID assigned by the bank
Modelnumber101Smart contract version ID, uniquely identifies the template or variant
Stylenumber101Parent version linkage, present only on variant entries, derived from PARENT_VERSION tag (numeric ID only)

TM Tag Mapping Logic

TM tags[] ValueBIAN Mapping Rule
tags[i] === LEVEL_TEMPLATEMap to ProductPriority = LEVEL_TEMPLATE
tags[i] === LEVEL_VARIANTMap to ProductPriority = LEVEL_VARIANT
tags[i] contains PARENT_VERSIONMap to ProductIdentification with ProductIdentificationType = Stylenumber; extract numeric ID only (e.g. 101, not PARENT_VERSION=101)

ProductReference[] Key Characteristics

CharacteristicDetail
Template entries2 entries in ProductIdentification[]: Suppliersitemnumber + Modelnumber
Variant entries3 entries in ProductIdentification[]: Suppliersitemnumber + Modelnumber + Stylenumber
All entries share same product_idVia Suppliersitemnumber, identifies the product family
Root-level CR fieldsDirectoryEntryDateType, DirectoryEntryDate, DirectoryEntryStatus sit outside the ProductReference[] array

ProductVersion carries the display version from TM (e.g. 1.0.0, 1.1.0), distinct from the smart contract version ID stored in Modelnumber.

Custom BIAN-Compliant Endpoint, Product Listing

A new custom endpoint compliant with BIAN Behavior Qualifier type is introduced to support product catalog page load:

  • Endpoint: GET /ProductDirectory/Product/Retrieve
  • Purpose: Lists all products available in TM. Internally mapped to GET /v1/products.
  • Filter applied internally: is_internal = false, excludes test and internal products.
  • Response: ProductListing[] array, high-level product records only, used to render product family cards.

Sales & Marketing BQ, Design

The Sales and Marketing BQ captures marketing-related definitions, features, pricing, and eligibility information for a specific product version (template or variant).

BQ Identification

  • salesandmarketingid = TM smart contract version ID (same value as Modelnumber in ProductReference[]).
  • The BQ payload is an array of elements, not a single object.
  • Endpoint: GET /ProductDirectory/{productdirectoryid}/SalesandMarketing/{salesandmarketingid}/Retrieve

ProductFeatureSpecification Logic, Template vs Variant

The adapter applies different transformation logic depending on whether the version is a template or variant:

  • LEVEL_VARIANT: maps directly to product_versions.params.value.
  • LEVEL_TEMPLATE (conditional):

◦ If params[i].number exists → format as range(min: X, max: Y, step: Z)

◦ If params[i].values exists → format as values(option1, option2, ...)

◦ If params[i].account exists with key-value pairs → flatten to key: value, ...; if empty → leave blank

◦ Else → map to params[i].value

Product Navigation Flow

The Product Directory supports a structured navigation flow from product families through templates to variants:

StepTriggerBIAN EndpointResult
5.1Page loadGET /ProductDirectory/Product/RetrieveProduct family cards
5.2Family card auto-loadGET /ProductDirectory/{id}/RetrieveTemplate cards (filtered front-end)
5.2aClick template Base Product IDGET /ProductDirectory/{id}/SalesandMarketing/{smid}/RetrieveTemplate features tab
5.3Click View ProductsNone, client stateVariant cards (zero API calls)
5.3aClick variant cardGET /ProductDirectory/{id}/SalesandMarketing/{smid}/RetrieveVariant features tab

Step 5.3 Efficiency: Zero additional API calls are made when listing variants. The ProductReference[] array retrieved in step 5.2 is held in client state and filtered entirely on the front end, variant navigation is instantaneous with no server load.

Front-End Filter, Variant Listing (Step 5.3)

Both conditions must be satisfied simultaneously:

  • ProductPriority === LEVEL_VARIANT
  • ProductIdentification[] contains an entry where ProductIdentificationType === Stylenumber AND IdentifierValue === Modelnumber of the selected template

Level of Detail Captured

Data captured must be:

  • Product-level, relates to a specific product family, template, or variant.
  • Configuration-driven, sourced from TM product version parameters and tags.
  • Variant-specific, each version (template or variant) has its own parameter set.
  • Institution-defined, not customer-specific or runtime-dependent.

Explicitly excluded: customer-specific settings, account-instance data, runtime balances or transaction states.

Implementation Priority

  • GET /ProductDirectory/Product/Retrieve, Custom endpoint for product family listing
  • GET /ProductDirectory/{productdirectoryid}/Retrieve, CR retrieval with ProductReference[] array
  • GET /ProductDirectory/{id}/SalesandMarketing/{salesandmarketingid}/Retrieve, Sales & Marketing BQ retrieval
  • Operations, Servicing, Production BQs, future phases when metadata sources are available

Related Service Domains & Systems

Related SD / SystemRelationship

Implementation Notes

Pagination Handling

When calling the product-versions API, the adapter must always pass the page token together with the product_id. Paginating with only the product_id returns only the first page. Both parameters must be included in every paginated request to ensure all product variants are retrieved.

Dev Environment Filtering

In the Dev environment, the products API may return test or internal products. The adapter must apply filtering to exclude such products before returning results to the Product Management application, based on agreed metadata or identification rules.

Smart Contract Upload Requirements

For products and their variants to be visible through the TM adapter, corresponding smart contracts must be created and uploaded in Thought Machine. Products that have not been uploaded will not appear in Product Directory results.
