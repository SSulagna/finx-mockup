Savings Account

The Savings Account service domain maintains and exposes the operational state of a specific savings <code>AccountInstanceReference</code>: balances, restrictions, entitlements, lifecycle attributes, and currency denominations. It is the live runtime view of a single savings account.

Scope. This SD owns runtime account state. Product agreement configuration lives in Sales Product Agreement; the customer holdings registry lives in Customer Product & Service Directory; customer profile lives in Party Reference Data Directory.

Service Domain Overview

The Savings Account Service Domain in BIAN v14.0.0 is responsible for managing and exposing the live operational representation of a savings account instance. It is a runtime, instance-level domain, not a contract or directory domain.

SD Scope, What It Manages

What This SD Manages

  • Runtime account state (status, lifecycle)
  • Account balances (available, incoming, outgoing)
  • Account currencies (base and secondary)
  • Account dates (open, effective, creating)
  • Entitlement option definitions, product-level parameters
  • Entitlement option settings, account-level parameter overrides
  • Restriction option definitions, restriction templates
  • Restriction option settings, restriction instances
  • Account identification and account name

What This SD Does NOT Manage

Excluded ConcernHandled By
Customer profile dataParty Directory SD
Product agreement configurationSales Product Agreement SD
Customer holdings registryCustomer Product & Service Directory SD
Product design / product catalogueProduct Directory SD

Behaviour Qualifiers (BQs)

No new Behaviour Qualifiers were introduced in this implementation. All enhancements remain inside the existing Savings Account SD structure, ensuring full BIAN alignment with no domain boundary violation.

The three standard CR-level operations are implemented:

OperationEndpointPurpose
InitiatePOST /SavingsAccount/InitiateCreates the Control Record for the account instance. Account status starts as PENDING. No parameters are set at this stage.
UpdatePUT /SavingsAccount/{id}/UpdateApplies parameters, updates account status (PENDING to OPEN), and reflects ongoing lifecycle changes (balance, status, restriction, currency changes).
RetrieveGET /SavingsAccount/{id}/RetrieveReturns the full operational state of the account including balances, parameters, dates, and restrictions.

Account Lifecycle States

The SD manages the following account lifecycle state transitions:

From StateTo StateTrigger
(none)ACCOUNT_STATUS_PENDINGPOST /SavingsAccount/Initiate, CR created, core account provisioned

BIAN SD Invocation Scenarios

Account Dashboard View

When a customer logs into mobile banking, the application calls Retrieve to display balances, currency, status, account details, and parameters. This is a read-only call to the SD.

Balance Inquiry

When a user requests their current balance, the SD Retrieve operation returns the AccountBalances[] array, which contains AvailableBalance, ExpectedIncomingBalance, and ExpectedOutgoingBalance.

Product Rule Display

When the UI needs to display product rules (e.g. minimum withdrawal limits), the EntitlementOptionDefinition[] array from the Retrieve response contains these product-level parameter definitions.

Re-invocation Triggers (Lifecycle Updates)

The Update operation must be re-invoked whenever any of the following occur:

  • Balance changes
  • Account status changes
  • Restriction changes
  • Parameter overrides applied
  • Currency changes

Freeze and Unfreeze Account

  • The bank operator can freeze or unfreeze an account, restricting all transactions to and from it.
  • This operation triggers when the update API is called and the fields for restriction templates and instances are populated.
  • Only the bank operator can initiate this operation; customers cannot request a freeze or unfreeze.
  • Only transactions are restricted on frozen accounts; customers can still access their accounts and view documents.
  • No notification is sent to customers when their accounts are frozen or unfrozen.

BIAN Structural Enhancements, Proposed Changes to Standard

The following enhancements to the BIAN v14 standard are recommended based on implementation experience:

EnhancementRationale
Array-based attribute standardisationAccountCurrency, AccountBalance, AccountDate, EntitlementOptionDefinition/Setting, RestrictionOptionDefinition/Setting should all be defined as arrays. Real implementations always contain multiple values.
Standard BalanceType enumerationBIAN should prescribe standard enums: AvailableBalance, ExpectedIncomingBalance, ExpectedOutgoingBalance, to prevent institution-specific naming.
DepositLimit as stringChanged from object to string to resolve circular referencing in the YAML schema definition.
No new BQ introducedAll enhancements retained inside existing SD structure. No domain boundary violation. Full BIAN alignment maintained.
