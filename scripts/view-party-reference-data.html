Party Reference Data Directory

The Party Reference Data Directory service domain maintains the authoritative master record of customer profile data: identifiers, names, contact details, document references, and consent history. Other service domains read party data from here; they do not duplicate it.

Scope. This SD owns customer master data. Lifecycle orchestration belongs to Party Lifecycle Management; document artifacts belong to Document Directory; agreement terms belong to Customer Agreement.

What Is This Service Domain?

In BIAN v14.0, the Party Reference Data Directory (PRDD) Service Domain maintains a consolidated master registry of Party profiles used across the enterprise.

Role: PRDD acts as the authoritative master index (registry) of Party identities and key reference attributes across all banking systems. It provides a canonical Party profile that all downstream systems rely on, eliminating the need for each SD to maintain its own party structure.

Key Classification: This is a Catalog / Directory Domain, not a Processing Domain. It stores lightweight, canonical, identity-focused, non-transactional data.

When to Use This Service Domain

Invoke PRDD whenever a system needs a validated, canonical Party identity or reference data, instead of querying heavy Core Banking Systems.

ScenarioActionPRDD Endpoint
New Individual Customer onboarded in CBSRegister CR to assert party existence and type; populate demographics and reference BQsCR Register + BQ Demographics + BQ Reference Update
Customer applies for MortgageLoan Origination SD queries PRDD to validate party, confirm type, retrieve KYC and risk classificationCR Retrieve + BQ Reference Retrieve
Mobile app loads customer profileApp queries PRDD to retrieve display name, classification, status, and linked identifiers without hitting CBSCR Retrieve
AML system performs screeningSystem retrieves Party profile, identifiers, and classifications before screeningCR Retrieve + BQ Reference Retrieve

During Party Creation (Onboarding)

Scenario: A new Individual Customer (John Doe) is created in Core Banking.

Action: Once CBS confirms party creation and returns the new Party ID, the orchestration layer calls POST /PartyReferenceDataDirectory/Register. A CR is created to assert party existence, party type, and directory entry identifier. All downstream systems then use this same Party reference.

During Product Origination

Scenario: Customer applies for a Mortgage.

Action: The Loan Origination system queries PRDD to validate party existence, confirm party type (Individual/Corporate), retrieve KYC classification, and retrieve risk category. This prevents each SD from storing its own party structure.

During Servicing (Mobile App)

Scenario: A mobile app loads customer profile data.

Action: The app queries PRDD to retrieve display name, party classification, status (Active/Suspended/Deceased/Dormant), and linked identifiers, without querying heavy core systems.

During Compliance / Risk Checks

Scenario: AML system performs screening.

Action: System retrieves Party profile, identifiers, and classifications from PRDD before screening. Ensures consistent, canonical identity data for compliance checks.

Control Record & Behavior Qualifier Structure

One Control Record (CR) is created per party. BQ cardinality varies:

CR / BQDescription & Cardinality
CR, CustomerProductAndServiceDirectoryEntryOne CR per party. Holds PartyReference, PartyName, PartyIdentification[], PartyType, DirectoryEntryDate.
BQ Demographics1:1 with CR. Socio-EconomicClassification, Ethnicity, Religion, Employment, EducationHistory.
BQ Reference1:1 with CR. KYC data, addresses, contact details, political exposure, CustomerSinceDate.
BQ Associations1:N with CR (array). Party relationships and associations, multiple records per party.
BQ Bank Relations1:N with CR (array). Bank relationship records, multiple records per party.
BQ CorePartyProfile (Non-BIAN)1:1 with CR. Utility BQ for Core Banking System party creation. Contains CorePartyProfileDetails.
BQ DirectoryRecord (Non-BIAN)Search BQ. Accepts Filter/FilterCriteria and returns DirectoryRecordDetails for matched parties.

Cardinality Rule: Associations BQ and Bank Relations BQ are 1:N (array) with the CR. All other BQs are 1:1 with the CR.

When and How to Invoke

PRDD is invoked at party creation and at any subsequent lifecycle event requiring identity or reference data update:

StepEndpointPurpose
A, Register CRPOST .../RegisterAssert party creation; record party type and directory entry identifier
B, Update DemographicsPUT .../Demographics/{id}/UpdatePopulate socio-economic, employment, and education data
C, Update ReferencePUT .../Reference/{id}/UpdatePopulate KYC, addresses, contacts, political exposure
D, CorePartyProfile RegisterPOST .../CorePartyProfile/RegisterCreate party in CBS using structured CorePartyProfileDetails (Non-BIAN Utility API)

Non-BIAN Utility API Endpoints

Two Non-BIAN Utility API endpoints extend PRDD for CBS-specific operations:

  • CorePartyProfile/Register, Sends structured party data to CBS for core party creation. Accepts CorePartyProfileDetails containing Salutation, NameInformation, EmailAddress, MobileNumber[], DateOfBirth, PartyIdentificationValue, CorePartyCountry. Uses CIF ID (format: CIFXXXXXXXXXX) as party identifier.
  • DirectoryRecord/Register, Party search endpoint. Accepts Filter and FilterCriteria objects; returns DirectoryRecordDetails of matched parties. Supports search by CustomerReference, ProductReference, OfferReference, and other business identifiers.
